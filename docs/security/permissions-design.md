# طرح پیشنهادی: سامانهٔ دسترسی و دامنهٔ داده — STM نسخهٔ ۳

**وضعیت:** پیشنهاد، برای تأیید شما · **وابسته به:** `permissions-audit.md` (۱۲ یافته)
**هدف:** هر کاربر دقیقاً و فقط همان چیزی را ببیند و بتواند که شما اجازه داده‌اید — نه یک ردیف بیشتر.

---

## ۱. پنج اصلی که طرح بر آن‌ها بنا شده

1. **بسته به‌طور پیش‌فرض (fail-closed).** نبودِ مجوز یا نبودِ دامنه یعنی «هیچ»، نه «همه». هر مسیری که مجوز صریح نداشته باشد، رد می‌شود.
   *امروز برعکس است: دامنهٔ خالی = دسترسی کامل (F-02).*
2. **یک منبع حقیقت.** تصمیم دسترسی فقط در یک ماژول (`web/scope.py`) گرفته می‌شود؛ نه در ۹۷ مسیر به‌صورت پراکنده.
3. **دفاع لایه‌ای.** UI چیزی را که مجاز نیست نشان نمی‌دهد (لایهٔ ۱)، API درخواست غیرمجاز را رد می‌کند (لایهٔ ۲)، و کوئری SQL فقط ردیف‌های مجاز را برمی‌گرداند (لایهٔ ۳). اگر یکی شکست، دو تای دیگر می‌گیرند.
4. **کمترین امتیاز.** مجوز «آپلود» نباید «دیدن پرسنل» بدهد؛ مجوز «تأیید» نباید «پاک کردن ماه» بدهد. هر عمل، مجوز خودش را دارد.
5. **قابل حسابرسی.** هر تصمیم رد/قبول و هر مشاهدهٔ دادهٔ حساس، در `access_log` ثبت می‌شود.

## ۲. مدل داده: «مجوز مبتنی بر دامنه» (Scope Grant)

به‌جای دو لیست JSON تخت، یک جدول سلسله‌مراتبی:

```sql
CREATE TABLE IF NOT EXISTS user_scopes (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id     INTEGER NOT NULL REFERENCES auth_users(id) ON DELETE CASCADE,
    deputy      TEXT NOT NULL DEFAULT '*',   -- '*' یعنی همهٔ معاونت‌ها
    center      TEXT NOT NULL DEFAULT '*',   -- '*' یعنی همهٔ مراکز آن معاونت
    supply_type TEXT NOT NULL DEFAULT '*',   -- 'تامین' | 'پخش' | 'تولید' | '*'
    created_at  TEXT DEFAULT CURRENT_TIMESTAMP,
    created_by  INTEGER,
    UNIQUE(user_id, deputy, center, supply_type)
);
```

سه نوع مجوز که با همین یک جدول بیان می‌شوند:

| قصد شما در پنل | رکورد |
|---|---|
| همهٔ سازمان | `('*', '*', '*')` |
| کل معاونت برون‌مرزی | `('معاونت برون مرزی', '*', '*')` |
| فقط شبکه فیلم | `('معاونت سیما', 'شبکه فیلم', '*')` |
| شبکه تهران، فقط پخش | `('معاونت سیما', 'شبکه تهران', 'پخش')` |
| چند مرکز پراکنده در معاونت‌های مختلف | چند رکورد `(deputy, center, '*')` |

**قاعدهٔ تصمیم:** یک ردیف داده دیده می‌شود اگر **حداقل یک** grant با آن مطابقت کند (OR بین grantها، AND داخل هر grant). این دقیقاً همان چیزی است که شما توصیف کردید: «معاونت برون مرزی و شبکه فیلم را مجوز بدهم → اطلاعات همان‌ها».

کوئری تولیدشده:

```sql
AND ( (r.deputy = 'معاونت برون مرزی')                       -- grant ۱: کل معاونت
   OR (r.deputy = 'معاونت سیما' AND r.cost_center = 'شبکه فیلم') )   -- grant ۲: یک مرکز
```

**سازگاری با دادهٔ فعلی:** در مهاجرت، `allowed_deputies` به `(d, '*', '*')` و `allowed_centers` به `(deputy_of_center, c, '*')` تبدیل می‌شود. ستون‌های JSON حذف نمی‌شوند (فقط دیگر خوانده نمی‌شوند) تا اگر لازم شد برگردیم. `scope_all_deputies`/`scope_all_centers` هم به `('*','*','*')` نگاشت می‌شوند.

## ۴. ماژول `web/scope.py` (هستهٔ کار)

```python
# امضاهای پیشنهادی
get_grants(user_id)                       # لیست grantها؛ admin → [('*','*','*')]
scope_sql(alias='r', user_id=None)        # (clause, params) آمادهٔ چسباندن به WHERE
is_row_visible(user_id, deputy, center, supply_type) -> bool
effective_centers(user_id)                # لیست مراکز مجاز (برای پر کردن dropdown)
require_data_perm(perm, scope_key=None)   # دکوریتور ترکیبی: مجوز + دامنه
```

نکتهٔ کلیدی `scope_sql`: برای کاربر بدون هیچ grant، `(" AND 1=0", [])` برمی‌گرداند — یعنی **صفر ردیف**، نه همه‌چیز.

سه الگوی استفاده، برای هر نوع مسیر:

```python
# ۱) مسیرهای داده‌ای با فیلتر ساختاری
clause, params = scope_sql('r')
sql = f"SELECT ... FROM records r WHERE 1=1 {clause}"

# ۲) مسیرهای تجمیعی/دستی (پرسنل، مراکز، قوانین)
centers = effective_centers(uid)          # ['شبکه تهران', 'شبکه فیلم']
sql += f" AND center_name IN ({','.join('?'*len(centers))})"

# ۳) عملیات تک‌ردیفی (تأیید، ویرایش)
if not is_row_visible(uid, row['deputy'], row['cost_center'], row['supply_type']):
    return jsonify({'error':'خارج از دامنهٔ دسترسی'}), 403
```

**اعمال اجباری:** یک `before_request` که فهرست مسیرهای مجاز به «بدون بررسی دامنه» را دارد (`/api/me`, `/login`, `/static/*`...). هر مسیر جدیدی که در فهرست نباشد و خودش دامنه اعمال نکند، **در تست CI شکست می‌خورد**. اینطور «۷٪ پوشش» هرگز برنمی‌گردد.

## ۵. جریان تأیید → پرداختی (رفع ایراد شما)

### وضعیت فعلی
- برای غیرادمین ۵۰۰ می‌دهد (F-01).
- دامنه را با «و» چک می‌کند، پس تأییدکنندهٔ معاونت‌محور قفل است (F-06).
- مقدار پرداختی را از `monthly_wage` می‌گیرد و در `monthly_payments` شیر می‌کند — این بخش درست است و نگه می‌داریم.

### جریان پیشنهادی

```
[۱] انتخاب ردیف‌ها در باکس «تأییدیه مدیر»  (فقط اگر box_approval + can_approve)
      ↓
[۲] POST /api/approval/bulk  {record_ids, decision}
      ↓ بررسی‌ها (همه داخل یک تراکنش):
      • مجوز can_approve
      • is_row_visible برای هر رکورد → رکورد خارج از دامنه: رد با پیام دقیق (نه ۵۰۰)
      • دورهٔ ماه باز باشد (is_period_open)
      • قفل بحرانی: رکوردی که قبلاً در monthly_payments با source='manual' ثبت شده،
        بازنویسی نشود (فقط گزارش شود)
      ↓
[۳] UPDATE calculated_results SET manager_approved=1, approved_by, approved_at
[۴] UPSERT monthly_payments (national_code, period_month) = دستمزد ماه، source='approved'
[۵] log_action + approval_log  → ردپای کامل: چه کسی، چه زمانی، چه مبلغی
      ↓
[۶] پاسخ: {approved: n, skipped: [{id, reason}], total_amount: m}
      ↓
[۷] UI: توست «۳ ردیف تأیید و در پرداختی مهر ثبت شد» + به‌روزرسانی جدول پرداختی
```

**قابلیت‌هایی که پیشنهاد می‌کنم اضافه شوند (خلاقیت):**

- **«تأیید گروهی معکوس‌پذیر»**: دکمهٔ «بازگردانی آخرین تأیید من» که از `approval_log` همان کاربر و همان ماه، عملیات را برمی‌گرداند.
- **«فقط ردیف‌های بدون ایراد»**: یک دکمه که به‌جای تیک زدن دستی، همهٔ ردیف‌های سبز (بدون اخطار) داخل دامنه را انتخاب می‌کند.
- **پیش‌نمایش اثر مالی پیش از تأیید**: «با تأیید این ۱۲ ردیف، ۴۳۰٬۰۰۰٬۰۰۰ ریال به پرداختی مهر اضافه می‌شود».
- **قفل ماه پس از تأیید نهایی**: بعد از تأیید همهٔ ردیف‌های یک مرکز، وضعیت آن مرکز «نهایی» شود و ویرایش بیشتر نیاز به ادمین داشته باشد.
- **اعلان**: در هدر، بَج «۷ رکورد منتظر تأیید شما» برای کسی که `can_approve` دارد و دامنه‌اش رکورد تأییدنشده دارد.

## ۶. UI: پنل مدیریت کاربران

فعلاً `users.html` چک‌باکس مجوز + دو لیست تخت معاونت/مرکز دارد. پیشنهاد:

```
│                  ● انتخاب‌شده:                            │

│     ▸ معاونت استان‌ها (۰ از ۳۱)                            │
│     هر مرکز: [نوع تأمین: همه ▾]                            │
│                                                            │
│ ۲) چه چیزی ببیند   ☑ داشبورد  ☑ نمودارها  ☐ جدول خلاصه     │
│                    ☑ گزارش   ☑ منابع انسانی  ☐ جست‌وجو کد ملی│

│                        [مشاهدهٔ ۵ ردیف نمونه]              │
└────────────────────────────────────────────────────────────┘
```

**پیش‌نمایش زنده** مهم‌ترین بخش این طراحی است: مدیر قبل از ذخیره، عدد می‌بیند — «این کاربر چند مرکز، چند رکورد و چند نفر را می‌بیند». بدون این، هیچ‌کس نمی‌داند دسترسی درست داده یا نه. (پیشنهاد می‌کنم این را در فاز ۲ اضافه کنیم.)

در سمت کاربر عادی:
- تب/باکس غیرمجاز **رندر نمی‌شود** (نه اینکه با CSS پنهان شود) → fail-closed.
- ستون «تأییدیه مدیر» فقط با `box_approval` ساخته می‌شود.
- نمودارها فقط برای دامنه؛ عنوان نمودار می‌گوید «دامنه: معاونت برون مرزی».
- در هدر، نام دامنهٔ فعال نمایش داده شود: «شما: شبکه فیلم و ۲ مرکز دیگر» تا کاربر بداند چرا اعداد کمتر از انتظار است.

## ۷. ایمپورت و پاک‌سازی، محدود به دامنه (F-05)

1. هنگام خواندن فایل، هر ردیف با `is_row_visible(deputy, cost_center, supply_type)` سنجیده می‌شود.
2. ردیف‌های خارج از دامنه نه ذخیره می‌شوند و نه حذف؛ در نتیجه به کاربر گزارش می‌شود: «۴۵ ردیف خارج از دامنهٔ شما نادیده گرفته شد».
3. `_safe_delete_records_for_month` باید دامنه بگیرد: `DELETE FROM records WHERE period_month=? {scope_clause}` — نه حذف کل ماه.
4. اگر فایل ردیفی از معاونت دیگر داشته باشد، گزینهٔ «درخواست ایمپورت کامل از مدیر» نمایش داده می‌شود (به‌جای اینکه بی‌صدا رد شود).
5. `/api/clear-month` فقط برای ادمین (یا با دامنه، و با تأیید دو مرحله‌ای).

## ۸. برنامهٔ اجرا — پنج گام آزمایشی

هر گام یک اسکریپت پایتون مستقل است که بکاپ می‌گیرد، اعمال می‌کند، diff نشان می‌دهد و `rollback_*.py` می‌سازد. **هیچ گامی روی نسخهٔ اصلی ذخیره نمی‌شود تا شما تأیید کنید.**

| گام | محتوا | ریسک | آزمون پذیرش |
|---|---|---|---|
| **۱** | رفع F-01 (تک‌خطی) + اصلاح منطق «یا» در تأیید (F-06) | خیلی کم | تأییدکنندهٔ معاونت‌محور می‌تواند تأیید کند؛ رکورد در `monthly_payments` ظاهر شود |
| **۲** | ساخت `web/scope.py` + جدول `user_scopes` + مهاجرت + fail-closed | کم (فقط زیرساخت) | کاربر بدون دامنه صفر ردیف ببیند (نه همه) |
| **۳** | اعمال دامنه روی مسیرهای خواندنی: گزارش، جدول خلاصه، نمودار، پرسنل، پرداخت، جست‌وجوی کد ملی، مراکز، قوانین | متوسط | همهٔ آزمون‌های ۱۲ یافته سبز شود (تست خودکار) |
| **۴** | بازطراحی `users.html` (درخت معاونت/مرکز + نوع تأمین + پیش‌نمایش) و پنهان‌سازی fail-closed در `index.html` | متوسط | مدیر بتواند «فقط شبکه فیلم» بدهد و کاربر همان را ببیند |
| **۵** | ایمپورت محدود به دامنه + `clear-month` ادمین‌محور + `access_log` | متوسط | ایمپورت کاربر محدود، دادهٔ بقیه را پاک نکند |

**مجموعهٔ آزمون خودکار** (خروجی مستقیم برای شما): یک اسکریپت `tests/test_permissions.py` که برای ۷ پروفایل کاربری (ادمین، معاونتی، مرکزی، نوع‌تامین، تأییدکننده، فقط‌خواندن، بدون‌دامنه) همهٔ ۲۴ نقطهٔ حساس را صدا می‌زند و جدول «چه چیزی دیده شد» را چاپ می‌کند. اگر یک ردیف خارج از دامنه برگردد، تست قرمز می‌شود.

## ۱۰. سه تصمیم که به تأیید شما نیاز دارد
